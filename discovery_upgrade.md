# Hayer discovery upgrade — "Got time" mode

This ledger specifies a second discovery mode alongside the existing swipe flow. It was drawn up on 12 September 2026 from the owner's brief, the reference product top-rated.online, and the Claude Design canvas at `references/app_discovery_mode_enhancement/Hayer Got Time.dc.html` (project `a9d09dd3-5dcb-4777-8d26-0850fb3b2600`, artboards 1a–1h and 2a–2b).

The app today offers one shape of decision: pick a place type, pick a deck size, pick solo or multiplayer, then swipe until something wins. That serves a user who wants an answer in a minute. It serves nobody who wants to research an area. "Got time" adds the second shape: browse every category present on the map, rank by six competing definitions of good, filter hard, and see it all on a map where the viewport is the query.

The two foundational requirements are shared by both modes: use Vela-derived non-API search and POI-detail extraction, and build one crowdsourced POI catalog in the backend. "In a hurry" (Swipe) and "Got time" (Discover) both read from and contribute to `hayer_poi_catalog`. As users search different areas, valid observations accumulate and refresh that common catalog, making later searches and place-detail reads cheaper and faster for everyone in either mode. Crowdsourcing here means aggregating provider observations generated by ordinary use, not requiring users to submit places manually.

Milestone placement is a new M8 so that M7 remains the invited-beta gate. The Discover surface and its harvesting ship dark behind a policy flag and can be enabled without a release. Shared source, catalog and detail services must continue serving Swipe independently of that flag.

## Decisions locked with the owner

- Construction is artboard 1c: a draggable sheet over a full-bleed map, with the map viewport as the query.
- Discover ends at "open a place and go". There is no hand-off into the swipe deck.
- Discover is solo, with a shareable result.
- The two modes have separate taxonomies, managed separately. Swipe stays an express mode with few categories. Discover gets a comprehensive tree whose branches appear and disappear according to what is actually in the result set.
- Categories are derived from data already in the catalog rather than harvested per leaf. See requirement 4.
- Amenities and review-text search are specified and rendered, but gated off, because the extractor does not capture the fields.
- The "Best" score ships as two admin-selectable formulas, compared on real data before one is locked in.
- Catalog attributes are promoted to generated columns rather than queried as JSON casts.
- Both modes use the same Vela-derived backend source for non-API search and available POI details, and the same durable, shared backend POI catalog. Separate taxonomies and ranking rules do not imply separate providers, caches or detail pipelines.

## Shared Vela source and crowdsourced backend catalog

This is a required architecture contract for every numbered requirement below, including ordinary Swipe searches, committed Discover searches, explicit deepening and place-detail reads.

Current evidence:

- Vela's reference implementation is in `references/Vela/core/src/main/java/app/vela/core/data/google/GoogleMapsDataSource.kt`, with request construction in `SearchPb.kt` and parsing in `parse/SearchParser.kt`. Hayer's backend adaptation lives in `backend/hayer_server/lib/src/places/google_web_place_source.dart`, `google_web_session.dart`, `search_pb.dart`, `search_parser.dart` and `google_response.dart`. `PlaceServices.forSession` selects the active calibration; `vela_calibration_feed.dart` and `vela_calibration_sync.dart` project and validate Vela's signed calibration updates. This is a Hayer backend adaptation of Vela source behavior, not a call to a Vela-hosted service or a Kotlin runtime embedded in Flutter.
- Hayer's `SearchParser._parseEntry` already extracts available name, coordinates, provider/feature ids, type, rating, review count, price, hours/status, address, phone, website, photo URLs and description/review snippets from search responses. `PlaceSource` currently exposes `search` only. In the checked-in Vela source, `GoogleMapsDataSource.placeDetails` at line 327 throws `CalibrationNeededException("placeDetails RPC not yet mapped")`; do not assume that an independent detail RPC is available to port. Search-derived snapshots are the working detail source for v1.
- `CatalogPlaceService.buildDeck` reads the backend catalog and uses `PlaceSearchService.buildDeckWithObservations` on a needed refresh, then persists observed candidates through `catalog_persistence.dart`. The catalog already stores more than the final swipe deck. The existing `_persist` helper, however, skips observations without matching swipe query evidence, and `GoogleWebPlaceSource._page` currently adds category evidence to every result. Both assumptions must be separated from raw source extraction to support broad discovery searches and focused detail refreshes correctly.

Required shared behavior:

1. **One provider adapter on the backend.** Both modes use a shared Vela-derived request/session/parser/calibration stack for Google Maps web search and the POI detail fields those responses contain. "Non-API" means this keyless web-extraction path, not an official Google Places Search/Details API integration. Flutter calls Hayer endpoints; it does not scrape Google directly. Do not introduce a mode-specific scraper, a paid Places API fallback or a second provider implementation. Preserve source attribution, active calibration, parser validation, bounded retries and the shared upstream request budget. Map tiles, reverse geocoding and directions retain their separate existing contracts.
2. **One durable catalog for all users and both modes.** Store canonical POIs in `hayer_poi_catalog`, keyed by `(provider, providerPlaceId)`, with shared snapshots, provenance, calibration version and freshness timestamps. Mode/user/session ids must not partition the POI cache. Mode-specific coverage, query evidence and session snapshots may remain separate metadata. A query miss or expired coverage never clears otherwise valid catalog rows; preserve the existing retention, quarantine and deletion policies rather than promising unbounded permanent storage.
3. **Every real source observation can contribute.** Use one observation-persistence service under both orchestrators. Persist all valid observed candidates within the bounded source operation, including candidates outside the displayed page, final deck or user-selected filters, before reducing results for presentation. Deduplicate by provider identity, preserve `firstSeenAt`, advance observation/freshness timestamps only after actual successful source observations, and preserve quarantine and independently recorded category evidence. A cache read does not make an old snapshot fresh. Failed/partial source responses must not erase a previously valid snapshot or mark unvisited query groups fresh.
4. **Read the cache first; search only when needed.** Swipe keeps its existing coverage/freshness/eligibility rules. A committed Discover area search first returns known catalog results and, when its canonical cell lacks fresh coverage, schedules one bounded shared-source harvest under requirement 12. Merely panning the camera, changing a sort or requesting another list page does not issue provider searches. Repeated searches by other users reuse fresh coverage or the existing in-flight job. "Deepen this area" explicitly requests another permitted pass under the same cooldown and budgets. Thus ordinary use of both modes grows the backend cache across areas; Discover does not depend exclusively on users discovering a separate refresh button.
5. **One cache-first POI-detail resolver.** Both modes resolve a selected POI by canonical provider identity through a shared backend detail service. Return fresh stored fields immediately. A fresh snapshot with sufficient fields, or one whose missing fields were recently checked, needs no provider request. If the snapshot is missing, stale or has not yet had a detail check for missing optional fields, use a bounded focused search through the same Vela-derived adapter, using trusted stored/session name and coordinates; update the requested place only when the returned provider id matches exactly. Other valid observations may still enrich the common catalog. An unavailable detail field is not permission to switch to an official API or repeatedly re-search the same place. Track the last attempted detail check separately, including no-match/partial outcomes, and dedupe/cool down refreshes per place across modes and users. Return allowed stale fields with their timestamp on failure; missing fields stay unavailable. A dedicated upstream detail RPC can be added later only when actually mapped, fixture-tested and canary-validated through this same shared adapter.
6. **Share data, preserve each mode's eligibility.** Discover immediately benefits from valid Swipe observations; Swipe benefits from Discover observations when its existing category-evidence rules are satisfied. Run the bounded compatibility queries in requirement 12 to obtain real swipe evidence; never invent it from a discovery alias or a detail lookup. Detail enrichment of the same POI is shared regardless of which mode requested it. Refreshing details does not rewrite an active swipe deck's membership, order, votes or session revision.
7. **Prove the loop across users and modes.** Integration tests must show user A searching area A in Swipe populates records reused by user B's Discover browse without another upstream request to retrieve those records; a cold Discover search in area B populates the shared catalog and valid compatibility evidence reused by a later matching Swipe search; and a detail refresh from either mode updates the same canonical record read by the other. Missing coverage for additional Discover domains may warrant a separate bounded harvest, but must not force re-fetching known records just to display them. Compare upstream request counts, not just UI output. Repeated views within freshness/cooldown bounds must not cause repeated extraction. Track unique POIs, newly observed cells, cache-hit rate and provider requests by initiating mode using aggregate metrics, so geographic growth and cross-mode reuse are measurable.

The required flow is: **either app mode → Hayer backend → shared catalog lookup → Vela-derived source only for needed search/detail refresh → shared observation persistence → mode-specific result or detail presentation**. Search/harvest scheduling may differ by mode; source extraction and POI storage must remain shared.

## Implementation decisions from plan review

These decisions resolve the implementation gaps reviewed on 12 September 2026. The numbered requirements below incorporate them; this is a plan update, not evidence that the feature has shipped.

- The URL owns the committed query. Camera movement and filter-sheet edits remain local drafts until the user applies them.
- Results are live. Keyset paging is exact over unchanged data, but does not promise a frozen result set across catalog updates.
- Map coverage is independent of list pagination, with bounded server aggregation for dense views.
- Discovery configuration is available before a swipe session exists. Place reporting also supports discovery without creating a session.
- Harvesting uses a bounded, versioned set of broad queries independent of the Discover tree, and preserves the distinction between catalog observations and proven swipe-category evidence. It is scheduled by a committed search with missing/stale area coverage or by an explicit deepen action; both use the same Vela-derived source and shared observation writer as Swipe.
- Disabled amenity controls retain their place in the design, with consumer-facing copy instead of the prototype's extractor explanation.

## 1. Home offers two modes of equal weight

Current evidence: `app/lib/features/home/home_screen.dart:157` builds a single `FilledButton.icon` labelled from `strings.newSearch` that pushes `/setup`, followed by outlined buttons for saved places, resume, join, and data and privacy. There is no second discovery entry point, and nothing on the screen tells the user that the swipe deck is a time-boxed choice rather than the only one.

Implementation:

- Replace the single primary button with the design's overline label "How much time do you have?" and two hero buttons of equal visual weight.
- "In a hurry" uses the `bolt` icon, the supporting line "Pick a vibe, swipe a deck, decide in a minute", and the chips "10 cards", "Solo or group", "~60 sec". It pushes `/setup`, whose behaviour is unchanged.
- "Got time" uses the `explore` icon, the supporting line "Dig through every place on the map, your way", and the chips "Sort & filter", "Hidden gems", "Full map". It pushes `/discover`.
- Leave saved places, resume, join, data and privacy, and the version indicator exactly as they are.
- Hide the "Got time" button entirely when the policy flag in requirement 15 is off or not yet known, so the build ships dark. In that state retain today's single primary entry and wording; apply the two-mode presentation only when enabled.

Acceptance:

- A fresh install with discovery enabled shows both hero buttons at equal weight, with the existing secondary actions below them, without creating or restoring a swipe session first.
- "In a hurry" reaches the existing setup flow with no behavioural change, verified by the existing setup and swipe tests still passing unmodified.
- With `discoveryEnabled` false, the "Got time" button is absent and no discovery route is reachable.
- Both hero buttons render correctly in Arabic and at the largest supported text scale.

## 2. Discover is a viewport-scoped surface, not a radius-scoped one

Current evidence: every existing place query is anchored. `CreateSessionRequest` carries `anchorLatitude`, `anchorLongitude` and `radiusMeters`; `_validateCreate` in `backend/hayer_server/lib/src/api/hayer_session_endpoint.dart:1449` clamps the radius to 500–10000 m; `nearbyCatalogByLocationSql` in `backend/hayer_server/lib/src/places/catalog_spatial_query.dart:3` filters with `ST_DWithin`. `SearchAreaMap` in `app/lib/core/widgets/search_area_map.dart:22` draws a single radius circle and is the only map in the app.

Implementation:

- Add a new route `/discover` in `app/lib/app/router.dart`, registered as a plain `GoRoute` alongside the existing screens. There is no shell route in this project and none should be introduced.
- Define the Discover query by a bounding box rather than an anchor and radius, so that "this view" in the UI and the counts in requirement 8 describe the same set of places.
- Use the full map widget bounds, including the portion behind the draggable sheet, with north-up bearing and zero pitch in v1. Sheet dragging must not change the query. Camera movement changes a pending viewport; "Search this area" commits it and starts a new query. While pending, label retained results "Previous area" rather than claiming that they match the new camera.
- On entry without a viewport, use the device location if already permitted, otherwise the last local discovery viewport, otherwise a Riyadh city view. Browsing never requires location permission. The location button requests permission only on use and stages a recentered viewport for the same explicit search action.
- Validate finite coordinates, latitude/longitude bounds, ordered bounds and supported-country scope on the server. Reject malformed or unsupported queries with a friendly message. Antimeridian-crossing queries are outside the supported GCC scope in v1. Default pages to 50 with a maximum of 100, text to at most 256 characters and selected taxonomy ids to at most 50. Apply browse/facet rate limits and database statement timeouts independently of harvest limits; return retry information while retaining prior results.
- Keep a user anchor for display purposes only. Distance per place is computed from the device location when available, and the `my_location` control recentres the camera without changing the query semantics.
- A committed search is a cache-first read plus, where coverage requires it, one bounded background harvest as specified in requirement 12. Show known results immediately and explain exploration in progress; filter-caused empty results must not trigger fresh harvesting of an otherwise fresh cell.
- Do not modify `_validateCreate` or the session radius bounds. Swipe's contract is unchanged.

Acceptance:

- Panning or zooming changes only the pending viewport. Searching commits the viewport and replaces the results, map features and facet counts as one query generation; late responses from earlier generations are ignored.
- Moving the sheet leaves results unchanged. Permission denial leaves browsing usable, and pending camera movement is not included in a shared link.
- After a committed search, the header reads as the design specifies, naming the area and "this view". Resolve the area label using the existing reverse-geocoding path, cache it by area and fall back to "This area" on failure; the label never controls query bounds.
- Creating a swipe session still validates radius exactly as before, verified by the existing endpoint tests.

## 3. Promote catalog attributes to generated columns

Current evidence: `backend/hayer_server/lib/src/storage/poi_catalog_row.spy.yaml` promotes only `name`, `normalizedName`, `countryCode`, `latitude`, `longitude` and `categoryIds`. Rating, review count, price level, primary type, opening hours, photos and status text exist only inside the `snapshot` JSON blob, and are read with `snapshot->>'field'` casts in `catalog_spatial_query.dart`. The only index that touches the blob is `hayer_poi_categories_gin` on `("categoryIds"::jsonb)`. Sorting or filtering on rating, review count or price today means an unindexed cast over the whole catalog.

Implementation:

- Add `STORED` generated columns to `hayer_poi_catalog` derived from `snapshot`: `rating`, `review_count`, `price_level`, `primary_type`, `lifecycle_status`, `completeness_mask` and `search_text`.
- Derive `lifecycle_status` with a `CASE` over normalized `statusText` into `temporarily_closed`, `permanently_closed` or `unknown`, recognizing the supported English and Arabic closure phrases. Absence of a closure phrase is not evidence that a place is open now; opening-hour badges use requirement 7. Exclude known temporary/permanent closures and quarantined rows from all discovery result and aggregate queries.
- Derive `completeness_mask` as a `smallint` bitmask recording the presence of photos, hours, phone, website, price and editorial summary. This is the data that backs the completeness filter in requirement 7.
- Derive `search_text` from null-safe concatenation of `normalizedName` and `editorialSummary` only. Exclude `featuredReview`, matching the shipped "names and descriptions" search promise and avoiding matches against review snippets suppressed on stale rows. Apply the existing stale-detail suppression when filtering descriptions as well as when displaying them.
- Guard numeric extraction by JSON type, range and integral-value checks before casting to the target column type. Invalid or out-of-range ratings, review counts and prices yield null; checking only `jsonb_typeof = 'number'` does not establish a safe target range. Validate array/object shapes before completeness or hours expressions too. Generated expressions must be immutable and valid on the deployed Postgres version.
- Start with the existing spatial index, a GIN trigram index on `search_text`, and candidate btree indexes on `rating`, `review_count`, `price_level`, `primary_type` and `"firstSeenAt"`. Make new catalog indexes partial on `WHERE "quarantinedAt" IS NULL`. Retain or refine indexes using representative query plans, including dense and sparse viewports and the computed Best score; do not assume every independent index helps a combined spatial sort.
- Put custom upgrade DDL into the new `migration.sql` and the resulting complete custom schema into its `definition.sql`, preserving the existing custom block. The comment at `migrations/20260909025500100-poi-issue-reports/definition.sql:1209` specifically identifies the definition as supporting fresh databases; it does not replace an upgrade migration. Register the migration and update schema-preservation tests. Measure generated-column backfill and index-build time on a populated test database before scheduling deployment.

Acceptance:

- Adding generated columns requires no changes to the existing persistence SQL. `catalogBatchUpsertSql`, `catalogEvidenceBatchUpsertSql` and `catalogCoverageUpsertSql` in `backend/hayer_server/lib/src/places/catalog_persistence.dart` are not edited, and every existing catalog persistence test passes without modification. Requirement 12 may add orchestration around these writers.
- Existing rows carry correct values immediately after the migration, because Postgres computes stored generated columns on add.
- Fresh creation and upgrade from the preceding populated schema both produce the columns, indexes and identical derived values while preserving existing custom DDL.
- Raw database fixtures with non-numeric, out-of-range and malformed optional fields insert successfully and yield null/absent derived values; typed snapshot deserialization is tested separately and is not made permissive by this migration.
- Record `EXPLAIN (ANALYZE, BUFFERS)` and timings for realistic spatial sorts and filters, including Best. Verify the bounding-box expression can use the existing geography index; any geometry cast requiring a different index must be explicitly supported. Do not force index use on tiny fixtures where a sequential scan is reasonable.

## 4. Derive Discover categories from observed primary types

Current evidence: the catalog classifies places by observation. A place qualifies for a category only when `hayer_poi_category` holds an evidence row proving the provider returned it for that category's query, written by `_persist` in `backend/hayer_server/lib/src/places/catalog_place_service.dart:413`. Each taxonomy entry therefore owns a search query string, and `PlaceTaxonomy.resolve` caps a session at five queries. Separately, the extractor already parses Google's own type label through the `category` calibration path into `PlaceSnapshot.primaryType`, stores it on every place, and renders it on the swipe card at `app/lib/features/swipe/place_card.dart:262` — but it is never used for classification or filtering anywhere in the codebase.

The owner posed the choice directly: either categorise on the fly, or build a comprehensive POI list first and then show or hide. The design settles it. Its tree leaves are named "Coffee shop", "Espresso bar", "Tea house", "Art gallery", "City park", "Steak house", "Fine dining"; its mock records carry `type: 'Coffee shop'`, `type: 'Japanese restaurant'`, `type: 'Art gallery'`. Those are the same vocabulary. The categories can be derived from data the catalog already holds.

Implementation:

- Treat the Discover taxonomy as an authored tree plus a mapping from observed `primary_type` values onto its nodes. Discover leaves carry no search query.
- Compute category counts as a `GROUP BY primary_type` over the current viewport, then roll them up the tree as the design's `nodeTotal` does: a node's total is its own mapped count plus the sum of its children.
- Hide unselected branches whose rolled-up total is zero, and show a footer stating how many categories are hidden. Explain that changing the area or clearing filters can bring them back. Keep selected zero-count nodes and their ancestors visible so users can remove the selection.
- Allow interior nodes to carry mappings of their own, so that a node such as Japanese or Middle Eastern counts places mapped directly to it as well as those under its children.
- Route any `primary_type` with no mapping into an "Other" bucket, and record its frequency for the admin report in requirement 16.
- Accept a list of aliases per node rather than a single string, because `primary_type` is provider free text and is language-sensitive: a place harvested under `language: ar` can store an Arabic label. Use one normalization function for publication validation and query matching. Each place maps to one node, then rolls up its ancestors. Unmapped or ambiguous types go to Other; `categoryIds` evidence informs admin mapping suggestions, but is not an implicit second classifier that disagrees with facet counts.

Acceptance:

- Adding a leaf to the Discover tree and mapping an already-observed type to it makes places appear under it with no scrape and no new migration.
- A viewport containing only cafes shows the Food and Drinks branch with its cafe descendants and hides the other eight domains, with the footer reporting the hidden count.
- Counts shown on a branch equal the sum of its descendants plus its own mapped places, proven by a unit test over a fixture tree.
- Swipe's classification is untouched: `hayer_poi_category`, `PlaceTaxonomy.resolve`, the five-query cap and the existing taxonomy admin page all behave exactly as before.

## 5. The Discover taxonomy is a separate, independently managed tree

Current evidence: the live taxonomy is a strict two-level model. `TaxonomyKind` is `category`, `cuisine` or `poiType`; validation in `backend/hayer_server/lib/src/places/taxonomy.dart:487` requires that categories have no parents and that every other item has at least one parent category, so deeper nesting is rejected outright. The bundled seed at `taxonomy.dart:6` holds three categories and fifty-three subcategories. The design's tree is nine domains and four to five levels deep, for example Food and Drinks, Restaurants, Cuisine, Asian, Japanese, Sushi. The owner's decision is that the two modes keep separate taxonomies rather than one being stretched to serve both.

Implementation:

- Add a table `hayer_discovery_taxonomy` modelled on the proven shape of `hayer_taxonomy_version`: the whole document as JSON, a `status` of draft, active or archived, a `revision`, validation results, and partial unique indexes enforcing one active and one draft.
- Model the document as an n-level tree of nodes carrying `id`, `labelEn`, `labelAr`, `emoji`, `children` and `typeAliases`. There is no search-query field.
- Seed the nine domains from the design: Food and Drinks, Things to Do, Accommodation, Entertainment, Wellness, Tours and Travel, Shopping, Activities and Sports, Religion and Worship.
- Validate unique ids across the whole tree, a depth ceiling of eight levels, labels present in both languages, and alias strings that are non-empty and unique tree-wide after normalization. Keep ids stable across edits; deleted ids in an old shared link are removed with a visible notice rather than silently interpreted as another category.
- Reuse the draft, validate, publish and rollback lifecycle already proven in `AdminEndpoint.taxonomyDraft`, `saveTaxonomyDraft`, `publishTaxonomy` and `rollbackTaxonomy`, each wrapped in a transaction with an audit row.
- Do not alter `hayer_taxonomy_version`, `TaxonomyKind`, `TaxonomyService` or `taxonomy_endpoint.dart`.

Acceptance:

- Publishing a Discover taxonomy revision has no effect on swipe setup, whose categories continue to come from `client.taxonomy.current()`.
- Rolling back a Discover revision restores the previous tree and writes an audit row.
- Validation rejects a duplicate alias, a duplicate id and a node missing an Arabic label.

## 6. Six ranking modes, with two selectable Best formulas

Current evidence: no consumer endpoint accepts a sort parameter. Ranking is a hardcoded four-key comparator — review count, rating, distance, provider place id — written twice: as SQL at `backend/hayer_server/lib/src/places/catalog_spatial_query.dart:54` and again in Dart at `backend/hayer_server/lib/src/places/place_search_policy.dart:102`. Any change to scoring that lands in one and not the other makes the cache-hit path and the live path disagree.

Implementation:

- Add `backend/hayer_server/lib/src/places/discovery_query.dart` as a single raw parameterised SQL builder, beside `catalog_spatial_query.dart` and constructed the same way. Discover ranking is defined once, in SQL, and never duplicated in Dart.
- Do not modify `catalog_spatial_query.dart` or `place_search_policy.dart`. Swipe's ranking, its closed-place guard and its price ceiling are out of scope.
- Implement the six modes the owner asked for and the design specifies, each with its user-facing explainer rendered under the result count: Best ("Rating weighted by how many people rated it"); Top rated, ordered by rating descending ("Highest rating first, any review count"); Most reviewed, ordered by review count descending ("The busiest places in this view"); Hidden gems, rating at or above 4.5 with fewer than 500 reviews ("4.5+ on fewer than 500 reviews"); Worst rated, ordered by rating ascending ("Lowest rating first — useful for ruling out"); Recently discovered, ordered by `firstSeenAt` descending ("Newest to our catalog").
- Implement Best as two expressions selected by policy. `popularityWeighted` is the design prototype's `rating * log10(review_count + 10)`. `bayesian` is `(v/(v+m))*R + (m/(v+m))*C`, where `v` is the review count, `R` the rating, `m` a positive shrinkage prior and `C` the catalog mean rating captured in the policy revision. Compare both on a fixed Riyadh fixture before choosing the launch default. The popularity expression ranks a 4.0 with 100,000 reviews above a 4.9 with 300; the Bayesian outcome depends on `m` and `C` and must be asserted using explicit fixture values.
- Hold the gem thresholds, the shrinkage prior, the global mean and the minimum-review floors as policy values rather than constants.
- Order every mode by its sort key then `providerPlaceId`, reusing the tie-breaker the existing query already relies on.
- Hidden gems is a qualifying filter followed by rating descending and the id tie-breaker. Require a known rating and at least one review, with policy-controlled lower and upper review bounds. Top/Worst rated require a known rating; Best requires a known rating and review count. Most reviewed and Recently discovered retain unknown optional fields with explicit nulls-last ordering where applicable. Missing ratings never become zero-star places.
- Return the policy revision and effective badge thresholds with discovery configuration. Gem pin styling, detail badges and explainers use those same thresholds; changing a formula or threshold starts a new query generation and invalidates old cursors. Interpolate the gem explainer from policy rather than hardcoding 4.5 and 500 in translations.
- The graveyard mode offered by top-rated.online is out of scope. Neither the brief nor the design asks for it, and `lifecycle_status` from requirement 3 makes it a later addition rather than a rewrite.

Acceptance:

- Each of the six modes orders a fixture set exactly as specified, proven by integration tests against real PostGIS.
- Switching the Best formula in admin changes the ordering without a client release.
- Swipe deck composition over identical input fixtures is unchanged, proven by existing session endpoint tests. Real decks may gain places as the shared catalog grows; their ranking and eligibility rules remain unchanged.

## 7. Advanced filters over the current view

Current evidence: `CreateSessionRequest` accepts a category, up to five subcategories, a price level treated as a maximum, an anchor, a radius, a deck size and an optional `visitAt`. It accepts no minimum rating, no minimum review count, no review-count band, no text query and no completeness signal. Opening hours are stored as a structured `OpeningPeriod` list inside the snapshot and are evaluated post hoc in Dart by `PlaceAvailability.isOpenAt`.

Implementation:

- Tree selection: selecting a node includes places mapped to it or its descendants. Multiple selected nodes are ORed; remove redundant descendant selections when a parent is selected. Different filter groups are ANDed. Other is selectable and uses the same mapping rule as facets.
- Number of reviews uses six disjoint integer bands: 1–49, 50–99, 100–249, 250–499, 500–999 and 1,000+. Bands are ORed and each has a histogram count. Unknown and zero review counts remain eligible when no band is selected, and match no band otherwise. The rendered labels must reflect these exact boundaries rather than the prototype's overlapping labels.
- Price offers Any or an exact level from one through four, rendered using `app/lib/core/gcc_currency_symbol.dart` and the place country. Unknown prices match Any only; this does not inherit swipe's maximum-price semantics.
- Minimum rating as Any, 3.5+, 4+ and 4.5+.
- Opening-hour windows use place-local time from the existing supported-country UTC offsets, with one server-supplied evaluation instant per query generation. Open now contains that instant; Open late overlaps [23:00, 24:00) today; Open for breakfast overlaps [06:00, 11:00) today; Open Friday overlaps any time on the next Friday, including today if Friday. Selected windows are ORed. Use half-open intervals, including overnight spill into the following day and Sunday-to-Monday rollover. Unknown or malformed hours fail an explicit hours filter and display "Hours unavailable", never "Open now". Old snapshots cannot assert current openness; stale hours show unavailable until refreshed.
- Evaluate hours in SQL against validated snapshot arrays after spatial/type narrowing, and verify the actual query plan rather than assuming SQL predicate order determines execution order. Keep the existing Dart swipe availability semantics unchanged. Match SQL and discovery badge behavior against shared expected fixtures for time boundaries and country offsets. Re-evaluate a visible Open now query on resume and at the next minute boundary; reset pagination if membership changes.
- Text search over `search_text` using the trigram index from requirement 3.
- Data completeness, tested against `completeness_mask`, offers photos, opening hours, contact details and price. Selected requirements are ANDed; contact means a non-empty phone or website, photos/hours mean a valid non-empty list, and price means a valid price level. Apply the same stale-field visibility rules as the detail payload so hidden fields do not satisfy the filter.
- Paginate with an opaque, validated keyset cursor over the sort key and `providerPlaceId`, with explicit direction and null handling. Bind it to the canonical query fingerprint, taxonomy revision, scoring-policy revision and hours evaluation instant. An incompatible or expired cursor returns `query_changed` and prompts a fresh first page. Discovery does not use the existing swipe query's `LIMIT 500`, which remains unchanged.
- Results are live rather than a server-stored snapshot. Guarantee complete paging only while the qualifying rows and sort keys remain unchanged. Ratings and review counts can move during a scroll; deduplicate displayed ids and offer Refresh to rebuild the first page, count and map. ## Risks

- Extracting the shared observation writer is the highest-risk change in this plan, and it is the one place where Discover genuinely modifies code Swipe executes. Requirement 12 requires separating unconditional valid-POI upserts from optional query-evidence and coverage writes in `CatalogPlaceService`, and moving `GoogleWebPlaceSource._page`'s automatic evidence tagging into a Swipe-only query adapter. This is unavoidable: `_persist` at `backend/hayer_server/lib/src/places/catalog_place_service.dart:388` currently executes `if (directlyObserved.isEmpty) continue;`, so broad discovery observations would be silently discarded and the shared-catalog contract in this document would not hold. Read every "Swipe is untouched" statement in this ledger as a promise about observable behavior — ranking, evidence semantics, eligibility, coverage writes and deck composition over identical fixtures — not as a promise that no shared code is refactored. Land this refactor as its own change, before any discovery surface depends on it, with the existing swipe and catalog-persistence suites passing unmodified as the gate.
- `primary_type` is provider free text, unversioned and language-sensitive. Mapping needs operator upkeep, which is why the unmapped-types report in requirement 16 is part of the feature rather than an optional extra.
- Discover invites users to trigger scrapes. The per-user limit, the existing global budget and the single-cell harvest bound are all load-bearing, and should be reviewed against real usage before the flag is turned on broadly.
- Worst rated publishes negative information about real businesses. Requirement 10 extends the existing reporting UI/moderation workflow with a catalog-based endpoint; the current session-only `PlaceEndpoint.reportIssue` cannot be used unchanged. The correction action must be reachable from result cards.
- Coverage remains the honest limit of the feature. Over a cold area Discover shows little, and no amount of UI work changes that; only the crowd-sourcing loop does.
